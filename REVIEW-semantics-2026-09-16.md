# Ревью: семантические риски в правилах (2026-09-16)

Проверено по локальному master (`0a72ca7`). Речь только про пункт 1 из
общего ревью — случаи, где линтер может посоветовать неверный код.
Остальные пункты (enum'ы вместо строк, location-based фиксы, CI-матрица
версий Crystal) — отдельно, код под них не перепроверял.

## CAT-049 `ThreadNewToSpawn` — неверный совет, надо чинить

`src/catalyst/rules/thread_new_to_spawn.cr`: severity `warning`, confidence
`high`, советует заменить `Thread.new { ... }` на `spawn { ... }`.

Это неверно в общем случае: `Thread` — OS-поток, `spawn` — файбер на
текущем шедулере. Замена меняет модель исполнения (параллелизм,
блокирующие вызовы, thread-local состояние). Варнинг с high confidence за
такой совет — прямой путь к потере доверия: юзер один раз получит
сломанный код и выключит весь линтер.

Что делать — варианты от строгого к мягкому:
1. Удалить правило вообще. `Thread.new` в Crystal пишут осознанно и редко;
   ложных срабатываний там почти нет, а цена неверного совета — высокая.
2. Оставить, но только как `info` + confidence `low`, с явной оговоркой в
   description ("только если вам действительно нужен файбер, а не поток").
3. Средний вариант: срабатывать только когда видно, что поток не нужен —
   на практике это недетектируемо статически, так что честно это тот же
   вариант 2.

## CAT-050 `FiberNewToSpawn` — ок, оставить как есть

`src/catalyst/rules/fiber_new_to_spawn.cr`: срабатывает только на цепочке
`Fiber.new { ... }.resume`, severity `info`. Это единственный случай, где
совет корректен. Нюанс `resume` (выполнить сейчас) vs `spawn` (поставить в
очередь) — на уровне info допустим, но стоит одной строкой упомянуть в
description, чтобы перфекционисты не открывали ишью.

## CAT-008 `SelectFirstToFind` — дыра с арностью блока

`src/catalyst/rules/select_first_to_find.cr`, метод `select_first_call`:
проверяется только `target.block` на truthiness. Кейс
`select { |x, i| ... }.first` (блок с индексом) пройдёт проверку, а
предложенный `find` отдаёт в блок только элемент — индекс потеряется, код
сломается. Нужна проверка `block.args.size == 1` до срабатывания.

Заодно: автофикс там же делается regex'ом по тексту строки
(`line_text.sub(...)`) — многострочные чейны его развалят, гард
`fix == line_text` ловит только часть случаев. Кандидат на location-based
сплайсинг, когда дойдёте до пункта 2 общего ревью.

## CAT-015 `StructVsClass` — нормально как info, не повышать

`src/catalyst/rules/struct_vs_class.cr`: уже загардено лучше, чем казалось
издалека — только `info`, только ≤4 ivar'ов, нет superclass, в теле только
аксессоры/`initialize`. В таком виде держать можно.

Не делать: не поднимать до warning и не расширять эвристику. Оставшиеся
риски, которые статикой не покрыть: мутация через копии (value-семантика),
`same?`/identity-проверки где-то в другом месте кодовой базы,
невозможность наследования в будущем. Один такой кейс — и правило начнут
игнорировать целиком. Пусть живёт как мягкий хинт.

## CAT-042 `SleepZeroToYield` — завышен confidence

`src/catalyst/rules/sleep_zero_to_yield.cr`: severity `info` (ок), но
confidence `high`. Нюанс: `sleep(0)` идёт через event loop (таймер),
`Fiber.yield` — прямой yield шедулеру. На практике почти всегда
эквивалентно, но "почти" и `high` не сочетаются. Понизить до `medium` и
добавить полстроки в description про отличие.
